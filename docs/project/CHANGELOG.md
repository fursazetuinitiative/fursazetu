# Purpose

This document records significant changes made to the FursaZetu platform throughout its lifecycle.

Its purpose is to provide a clear historical record of decisions, improvements, fixes, and milestones while preserving the reasoning behind each change.

A well-maintained changelog improves transparency, accountability, collaboration, and long-term maintainability.

It allows developers, curators, contributors, and AI assistants to understand not only what has changed, but also why those changes were made.


# Changelog Principles

## Record Meaningful Changes

The changelog should capture changes that affect the platform, its users, or its development process.

Minor spelling corrections or insignificant formatting updates do not normally require an entry.


## Explain the Reason

Every change should answer two questions:

- What changed?
- Why was the change necessary?

Understanding the reason behind a decision is often more valuable than the change itself.


## Be Clear and Concise

Entries should be easy to read and understand.

Avoid unnecessary technical jargon unless it provides useful context.


## Preserve History

Entries should never be deleted.

If a decision is reversed, record the new decision rather than removing the original one.

The changelog serves as the historical memory of the project.


# Change Categories

To improve readability, classify changes using the following categories.

## Added

New features, pages, components, documentation, or capabilities introduced to the platform.


## Improved

Enhancements to existing functionality, usability, performance, accessibility, or workflows.


## Changed

Modifications to existing behaviour, architecture, structure, or standards.


## Fixed

Bug fixes, corrections, broken functionality, or inconsistencies that have been resolved.


## Removed

Features, components, plugins, pages, or documentation intentionally removed from the project.


## Deprecated

Features scheduled for future removal but retained temporarily for compatibility.


## Security

Changes related to security, permissions, authentication, data protection, or vulnerability mitigation.

```text
## YYYY-MM-DD

### Improved

-

### Changed

-

### Fixed

-

### Removed

-

-

### Security

-

### Reason

Brief explanation of why these changes were introduced.
```


# Versioning

FursaZetu follows Semantic Versioning.

Major Version (X.0.0)

Used for significant architectural changes, redesigns, or breaking changes.

Example:

1.0.0 → 2.0.0



Minor Version (1.X.0)

Used for new features that remain backward compatible.

Example:

1.2.0 → 1.3.0


Patch Version (1.0.X)

Used for bug fixes, documentation updates, performance improvements, and minor corrections.

Example:

1.0.3 → 1.0.4



# Example Entry

## 2026-07-21

Version: 1.0.0

### Added

- Brand guidelines.
- Site architecture.
- Opportunity Model.
- Editorial Policy.

### Improved

- Established standardized documentation structure across the project.

### Changed

- Adopted an opportunity-first platform architecture instead of a traditional blog approach.

### Reason

This release establishes the foundation of the FursaZetu platform and provides a shared framework for future development.



# Documentation Changes

Documentation updates should also be recorded whenever they introduce significant new standards or alter existing project direction.

Examples include:

- New development standards.
- Changes to editorial policy.
- Updated design principles.
- Revised SEO strategy.
- New automation workflows.
- Architectural decisions.

Documentation is considered part of the product and should evolve alongside the platform.


# Guiding Principle

Every significant decision contributes to the story of FursaZetu.

The changelog exists to preserve that story.

It provides a transparent record of how the platform has evolved, why decisions were made, and how continuous improvement has shaped the project over time.
